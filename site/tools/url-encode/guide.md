検索URLに日本語を入れたら、途中から %E3%81 だらけになった。
`&` や `/` をそのまま入れたら、パラメータが勝手に割れた。
どの方式で変換すればいいのか、毎回あやふやになる。
このツールは、encodeURIComponent と encodeURI の結果を切り替えて見比べられ、デコードと、URL からのクエリ分解（key と値の表）までブラウザ内でできます。

## 使い方

1. 上のラジオボタンで方式を選びます。クエリの値やパスの1区間だけを変換するなら encodeURIComponent、組み立て済みの URL 全体なら encodeURI です。
2. 「元の文字列」に入力すると、「エンコード後」に即座に結果が出ます。逆に「エンコード後」を書き換えると、「元の文字列」側がデコードされます。
3. 「スペースを + にする」にチェックを入れると、エンコード結果の `%20` がすべて `+` に変わります。チェックを入れたままデコードすると、`+` が空白に戻ります。フォーム送信の形式に合わせたいときの切り替えです。
4. 下の欄に URL を丸ごと貼ると、`?` 以降を key と値（デコード後）の表に分解します。`#` から後ろ（フラグメント）は表に含めません。

手順は以上です。エンコード結果は「コピー」ボタンで、そのままクリップボードに送れます。

## 仕組み・計算式

パーセントエンコードの規則は RFC 3986（URI の汎用構文）の 2.1 節にあります。文字を UTF-8 のバイト列にして、1バイトごとに `%` と2桁の16進数で表します。日本語のひらがな1文字は UTF-8 で3バイトなので、`%XX` が3つ並びます。「こ」が `%E3%81%93` になるのはこのためです。絵文字のような4バイトの文字は `%XX` が4つになります。

エンコードしない文字（非予約文字）は、RFC 3986 の 2.3 節で英字・数字・`-` `.` `_` `~` と決まっています。ただし、JavaScript の関数（ECMA-262 の encodeURIComponent / encodeURI）は少し違います。

- encodeURIComponent が残す文字は `A-Z a-z 0-9 - _ . ! ~ * ' ( )` です。それ以外は `/ : ? # & = +` を含めてすべて変換します。
- encodeURI は上の文字に加えて、`; / ? : @ & = + $ , #` も残します。URL の骨組みを壊さないための仕様です。
- どちらも、半角スペースは `%20` になります。

ここで1つ注意があります。`! * ' ( )` は RFC 3986 では予約文字ですが、encodeURIComponent は変換しません。厳密な RFC 3986 準拠の出力が必要なシステムに渡すなら、この5文字は自前で置き換える必要があります。

スペースの扱いは、規格が2つあります。RFC 3986 では `%20` です。HTML フォームの `application/x-www-form-urlencoded`（WHATWG URL 仕様）では `+` になります。「スペースを + にする」は、この2つの切り替えです。クエリの表の分解は、後者に合わせて `+` を空白として読みます。

## 計算例

ツールの script.js と同じ処理（encodeURIComponent / encodeURI / decodeURIComponent）を node で動かして確かめた値です。

**例1:encodeURIComponent で `こんにちは 世界 & 記号/example?` を変換。**
結果は `%E3%81%93%E3%82%93%E3%81%AB%E3%81%A1%E3%81%AF%20%E4%B8%96%E7%95%8C%20%26%20%E8%A8%98%E5%8F%B7%2Fexample%3F` でした。`&` は `%26`、`/` は `%2F`、`?` は `%3F` に変わっています。意外だったのは、ひらがな5文字だけで `%XX` が15個も並ぶことです。

**例2:encodeURI で `https://example.com/検索?q=a b&x=1#top` を変換。**
結果は `https://example.com/%E6%A4%9C%E7%B4%A2?q=a%20b&x=1#top` です。`://`、`?`、`=`、`&`、`#` は残り、「検索」とスペースだけが変換されました。同じ文字列を encodeURIComponent にかけると `:` と `/` まで変わってしまい、URL として使えません。

**例3（境界値）:`a b+c` を encodeURIComponent で変換し、「スペースを + にする」を切り替える。**
チェックなしでは `a%20b%2Bc`、チェックありでは `a+b%2Bc` でした。元の `+` は、どちらでも `%2B` です。この `%2B` が残っているから、デコード時に「元から + だった文字」と「スペースだった文字」を区別できます。

**クエリ分解の例。** `https://example.com/search?q=東京+タワー&page=2&empty=` を貼ると、表は3行になります。q は「東京 タワー」（`+` が空白に戻る）、page は 2、empty は空の値です。

## よくある間違い

**二重にエンコードする。** 変換済みの文字列に、もう一度かけていませんか？ すでにエンコード済みの文字列をもう一度変換すると、`%` が `%25` になります。`a b` を2回変換した結果は `a%2520b` です。サーバー側で `%20` に見えず、`%2520` という文字列が届くので、検索語が化けます。確かめるなら、変換結果を「エンコード後」欄に入れて、デコードが1回で元に戻るかを見てください。

**URL 全体に encodeURIComponent を使う。** `https://` の `:` と `/` が変わって、リンクとして開けなくなります。URL 全体なら encodeURI、クエリの値だけなら encodeURIComponent、と使い分けます。迷ったら、値だけを encodeURIComponent に通してから、自分で `?q=` につなぐのが安全です。

**`+` と `%20` を同じものだと思う。** パスの中の `+` は、ただの文字です。フォーム形式のクエリの `+` だけが空白を表します。デコードの前に `+` を空白へ置き換えるのは、フォーム形式のときだけにしてください。パスの `+` まで空白にすると、ファイル名のような文字列が別物になります。

## よくある質問

### Q. デコードで「不正な % エスケープシーケンス」と出ます。
A. `%` の後ろが2桁の16進数になっていないためです。`%GG` や、末尾が `100%` のような形がそうです。`%E3%81` のように UTF-8 の途中でちぎれたバイト列も、同じエラーになります。`%` を文字として使いたいなら `%25` と書いてください。

### Q. クエリの表に「（デコード失敗）」と出る項目があります。
A. その key か値に、不正な `%` が含まれています。表示は、デコードできなかった元の文字列に「（デコード失敗）」を付けたものです。元の URL の該当箇所を直すか、`%` を `%25` にしてください。

### Q. 日本語を含む URL を、そのまま貼っても大丈夫ですか？
A. はい。貼った URL を URL オブジェクトとして読めないときは、`?` より後ろを文字列として分けるので、エンコード前の日本語入りでも表は出ます。ただ、`#` 以降は読まない点は変わりません。

### Q. 絵文字や、文字コードが壊れた文字列でも変換できますか？
A. 絵文字は4バイトの `%XX` になって、普通に変換されます。壊れたサロゲート（対になっていない半端な文字）だけは、エンコードエラーとして赤字で表示されます。
