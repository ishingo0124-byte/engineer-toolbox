APIのレスポンスを前に、型を手で書き起こすのが面倒。
ネストが3段あると、どこまで書いたか分からなくなる。
配列の中に、キーがあったりなかったりする要素もある。
JSON を貼るだけで、ネストを分解した interface（または type）と、欠けたキーのオプショナル化、型が混ざった値のユニオン型までを出力します。

## 使い方

1. 左上の欄に JSON を貼り付けます。貼ると同時に下の欄へ型定義が出ます。ボタンを押す必要はありません。
2. 「ルート型の名前」に、最上位の型名を入れます。空欄のままなら Root になります。
3. 「出力形式」で interface か type（type alias）を選びます。

ここまでが必須の操作です。残りは見た目の好みの設定です。

4. 「readonly を付ける」と、全プロパティの前に readonly が付きます。「行末にセミコロン」を外すと、セミコロンなしの書式になります。
5. 「型定義をコピー」で、出力欄の中身をまとめてコピーできます。

## 仕組み・計算式

JSON の値は、JSON の仕様（RFC 8259）が定める6種類、つまり文字列・数値・真偽値・null・オブジェクト・配列に分けて見ています。変換の方針は次のとおりです。

- 文字列は string、数値は number、真偽値は boolean、null は null になります。
- オブジェクトは、キー名を PascalCase にした名前の interface（または type）として、別に切り出されます。
- 配列は `T[]` で表します。要素の型が混ざるときは `(A | B)[]` のように括弧つきのユニオンにします。
- 配列の中のオブジェクトは、全要素のキーの和集合を取ります。一部の要素にしかないキーには `?` が付きます。
- 同じキーに違う型の値が混ざっていれば、`number | string` のようなユニオン型にします。

この読み替えは、TypeScript Handbook の「Object Types」「Everyday Types」にあるオプショナルプロパティ、ユニオン型、配列型の書き方に沿っています。

配列の要素の型名は、プロパティ名を単数形にして作ります。items は Item、categories は Category です。末尾の s や ies を落とすだけの簡易な規則で、英語の文法を理解しているわけではありません。s で終わらない名前（たとえば data）には Item が足されて DataItem になります。同じ名前がもう一度必要になったときは、末尾に 2、3 と番号が付く作りです。

現場の落とし穴を先に書きます。出力は「貼ったサンプルに見えた範囲」だけの型です。サンプルに現れなかったキーや型は、当然ながら出てきません。

## 計算例

数字ではなく出力で確かめます。このツールの script.js を node で実行し、出力をそのまま写しました。

**例1: 初期表示のサンプル**

初期値の JSON（id、name、active、score、address、tags、items を持つオブジェクト）を、そのまま変換しました。出力は次のとおりです。

```
interface Address {
  pref: string;
  city: string;
}

interface Item {
  id: number;
  label: string;
  price?: number;
}

interface Root {
  id: number;
  name: string;
  active: boolean;
  score: null;
  address: Address;
  tags: string[];
  items: Item[];
}
```

items の2件目には price がないので、`price?: number` になりました。score は値が null だけなので、型も `null` だけです。

**例2: 形式を変える**

同じ JSON で、出力形式を type、readonly を ON、セミコロンを OFF にすると、`type Root = {` で始まり、各行が `readonly id: number` のように出ます。末尾の `}` にもセミコロンは付きません。

**例3: 型が混ざる、空、識別子でないキー（境界値）**

`{"values":[1,"a",null],"empty":[],"user-id":5,"data":[{"v":1},{"v":"x"}]}` を入れると、Root は次の形になりました。

```
values: (number | string | null)[];
empty: unknown[];
"user-id": number;
data: DataItem[];
```

DataItem の v は `number | string` です。空配列は中身の手がかりがないので `unknown[]` になります。ハイフンを含むキーは、ダブルクォートで囲まれて出ます。

ルートが配列のときも試しました。`[{"a":1},{"a":2,"b":true}]` を、ルート型の名前 Row で変換すると、`interface RowItem` に `a: number;` と `b?: boolean;` が出て、最後に `type Row = RowItem[];` が付きました。

## よくある間違い

### 1. 出力を、そのまま正しい型だと思ってしまう

正直なところ、一番気をつけてほしいのはここです。サンプルの1件では score が null でも、本番では数値が入る API は珍しくありません。このツールは null だけを見て `score: null` と出します。`number | null` に直すのは、仕様書を見られる人の仕事です。

確かめ方は、null が出たキーと空配列が出たキーだけを探すことです。そこが手直しの候補になります。

### 2. サンプルが1件だけで、オプショナルが出ない

配列の要素が1件しかなければ、すべてのキーが「ある」ことになり、`?` は付きません。実データでは欠けるキーがあっても、貼った JSON に現れなければ分かりません。欠けるケースを含む複数件を貼ってください。

### 3. number を、整数と小数の区別だと思っている

JSON の数値は、整数も小数も同じ number です。price が 1 でも ratio が 1.5 でも、出力はどちらも number でした。ID だけ文字列にしたい、特定の値だけ許したい、といった絞り込みは、出力のあとで手を入れる部分です。

### 4. 同じ形のオブジェクトが、まとまると思ってしまう

別々のキーに同じ形のオブジェクトがあっても、型は共通化されません。キーごとに別の interface が作られます。共通の型にしたければ、出力を見て自分でまとめてください。

## よくある質問

### Q. interface と type のどちらを選べばよいですか？
A. 貼った JSON から作れる範囲では、どちらでも同じ形のオブジェクト型になります。あとで extends で拡張したいなら interface、ユニオンなどと合成するなら type が使われることが多いです。チームの規約があれば、それに合わせてください。

### Q. JSON が不正なときはどうなりますか？
A. 出力欄は空になり、エラーが赤字で出ます。位置が分かる場合は「◯行目 ◯列目付近」が付きます。末尾のカンマ（`{"a":1,}` のようなもの）で試すと、1行目 8列目付近と表示されました。カンマの過不足や、シングルクォートの使用を疑ってください。メッセージの英語部分は、ブラウザの種類やバージョンで変わります。

### Q. 貼った JSON は外部に送られますか？
A. 変換はブラウザの中で動く JavaScript だけで行います。通信は発生しない作りです。

### Q. プロパティ名が日本語や記号のときは？
A. プロパティ名としては、ダブルクォートで囲んで出力します（`"住所": Root2;` のようになります）。ただし型名は英数字だけから作るので、日本語のキーが入れ子のオブジェクトだと、型名が Root になって Root2 のように番号が付きます。意味のある名前にしたければ、出力後に型名を置き換えてください。同じキー名（user など）が別の場所に出たときも、User、User2 と番号で区別されます。
