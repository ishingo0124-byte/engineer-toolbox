日本語を `btoa()` に渡したら、いきなり例外で止まった。
受け取った文字列が Base64 らしいけれど、中身が読めない。
テキストと Base64 を相互に変換します。日本語や絵文字は UTF-8 に直してから処理するので文字化けせず、URL-safe 形式と、76文字で折り返す形式にも切り替えられます。

## 使い方

1. 「テキスト」欄に文章を入力すると、下の「Base64」欄に変換結果が出ます。
2. 逆に「Base64」欄へ文字列を貼り付けると、「テキスト」欄にデコード結果が出ます。
3. URL やファイル名に使うなら「URL-safe」にチェックを入れます。`+` と `/` が `-` と `_` に変わり、末尾の `=` が消えます。
4. メールの本文などに入れるなら「76文字で改行する」にチェックを入れます。

3番と4番は、両方同時にチェックすることもできます。ただ、片方ずつ試して違いを見るほうが分かりやすいと思います。

デコードでエラーが出たときは、欄の下に理由が表示されます。「Base64として使えない文字」「長さが不正」「パディングの位置が不正」「UTF-8として解釈できない」の4種類です。

## 仕組み・計算式

Base64 は RFC 4648 で定義された、バイト列を64種類の ASCII 文字（A〜Z、a〜z、0〜9、`+`、`/`）で表す方式です。3バイト（24ビット）を6ビットずつ4つに分けて、1つずつ文字に当てはめます。そのため、データの大きさは約 4/3 倍になります。

バイト数が3の倍数でないときは、末尾を `=` で埋めます（RFC 4648 §3.2）。余りが1バイトなら `==`、2バイトなら `=` です。

URL-safe 版は RFC 4648 §5 の「base64url」です。`+` を `-` に、`/` を `_` に置き換えます。パディングは省略されることが多く、このツールのチェック時もそうしています。

76文字で改行する形式は、メールの MIME（RFC 2045 §6.8）に合わせたものです。1行を76文字以内にします。

文字列を扱うときは、先にどの文字コードでバイト列にするかが決まっていないと変換できません。このツールは、UTF-8（RFC 3629）に固定しています。`TextEncoder` で文字列を UTF-8 のバイト列にして、そのバイト列を Base64 にします。デコードは、逆の順に `TextDecoder` で読み戻します。

デコード側は少し寛容です。`-` と `_` は `+` と `/` に読み替え、パディングが足りなくても補います。空白や改行はすべて取り除くので、76文字折り返しのまま貼っても読めます。

## 計算例

数字や出力は、script.js と同じ処理を node で実行して確かめました。

**例1: 英数字と、パディングの長さ**

| 入力 | Base64 | URL-safe |
|---|---|---|
| Man | TWFu | TWFu |
| Ma | TWE= | TWE |
| M | TQ== | TQ |
| Hello | SGVsbG8= | SGVsbG8 |

「Man」は3バイトなので4文字ちょうどで、パディングは付きません。「Ma」は2バイトで `=` が1つ、「M」は1バイトで `=` が2つです。

**例2: 日本語と絵文字**

「あ」は UTF-8 で 3 バイトなので、Base64 は `44GC` になりました。「日本語」は 9 バイトで `5pel5pys6Kqe`、絵文字の 😀 は 4 バイトで `8J+YgA==` です。URL-safe にすると、最後は `8J-YgA` になります。

初期表示の「Hello, 世界！ / こんにちは、Base64。」は、`SGVsbG8sIOS4lueVjO+8gSAvIOOBk+OCk+OBq+OBoeOBr+OAgUJhc2U2NOOAgg==` になりました。

**例3: 境界値。`+` と `/` が出る入力**

「>>>???」を変換すると、通常は `Pj4+Pz8/` です。URL-safe にすると `Pj4-Pz8_` に変わります。この2つの文字を含む Base64 を、そのまま URL のクエリに入れると、`+` は空白と解釈されることがあり、`/` はパスの区切りと紛れます。

**例4: 76文字の折り返し**

「あ」を30個入れると、UTF-8 は 90 バイトで、Base64 は 120 文字です。「76文字で改行する」にすると、1行目が76文字、2行目が44文字になりました。

**例5: エラー**

`SGVs*` は「使えない文字」、`SGVsb` は「長さが不正」、`SGV=sbG8` は「パディングの位置が不正」でエラーになります。また、PNG ファイルの先頭部分にあたる `iVBORw0KGgo=` を入れると、UTF-8 として読めないというメッセージが出ました。

## よくある間違い

### 1. Base64 を暗号化だと思う

Base64 は、元に戻せる形式の変換です。鍵も何もありません。誰でも同じ手順で戻せます。中身まで隠れていると思っていませんか。パスワードや秘密のデータを Base64 にしただけでは、隠したことにはなりません。HTTP の Basic 認証（RFC 7617）も Base64 を使いますが、これはユーザー名とパスワードを ASCII の文字列にするための表現で、秘密にする仕組みではありません。

### 2. `btoa()` に日本語をそのまま渡す

ブラウザの `btoa()` は、1文字を1バイトとして扱います。日本語や絵文字を渡すと、例外（InvalidCharacterError）になります。このツールの手順どおり、まず `TextEncoder` で UTF-8 のバイト列にしてから渡す必要があります。

### 3. URL-safe と通常の形式を混ぜる

JWT（RFC 7515）のように URL-safe でパディングなしの形式を、通常の Base64 のデコーダーに渡して失敗することがあります。逆に、`+` や `/` を含む通常の形式を URL にそのまま貼る事故もあります。このツールのデコードは、両方を自動で読み替えるので、どちらを貼っても戻せました。

ただし、相手のシステムが厳格な場合は、どちらの形式を期待しているかを仕様で確かめてください。

### 4. 画像やバイナリのデコード結果が文字化けする

PNG や JPEG などのファイルを Base64 にしたものを貼ると、「UTF-8として解釈できないバイト列」というエラーになります。このツールはテキスト専用だからです。画像のデータなら、ブラウザやコマンドラインのツールでファイルとして戻す必要があります。

正直なところ、最初は「壊れた Base64 だ」と思い込みやすいのですが、実際には「テキストではないデータ」であるだけ、というケースが多いと感じます。

## よくある質問

### Q. デコードでエラーになるのは、どんなときですか？
A. 使えない文字が含まれる、長さが不正（余りが1文字になる）、`=` の位置がおかしい、デコードした結果が UTF-8 として読めない、の4つです。

### Q. URL-safe かどうかを区別して貼る必要がありますか？
A. ありません。デコードは `-` と `_` を自動で読み替え、パディングが足りなくても補います。`SGVsbG8` も `SGVsbG8=` も、「Hello」に戻りました。

### Q. パディング（=）はなぜ付いたり付かなかったりしますか？
A. 入力のバイト数が3の倍数でないときだけ、末尾を埋めるのが本来の形です。URL-safe では、省略する運用が多いためです。

### Q. 入力した内容はサーバーに送られますか？
A. 送られません。変換はブラウザの中だけで行います。
