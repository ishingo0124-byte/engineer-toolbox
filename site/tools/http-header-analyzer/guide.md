診断ツールで「セキュリティヘッダーが不足」と出たけれど、何を足せばいいのか分からない。
HSTS の max-age が秒で書いてあって、何日なのかピンと来ない。
Server や X-Powered-By を出しっぱなしにして大丈夫なのかも気になる。
`curl -I` の出力を貼るだけで、8種類のセキュリティヘッダーを4段階で判定し、漏えいしやすいヘッダーも別枠で指摘します。

## 使い方

1. `curl -I https://example.com/` の出力や、ブラウザの開発者ツール（Network）でコピーしたレスポンスヘッダーを、そのまま貼ります。`< ` が先頭に付いた `curl -v` 形式でも読めます。
2. 見つかったヘッダーが「名前・値・意味」の表で並びます。1行目の `HTTP/2 200` のようなステータス行は、件数に含まれません。
3. チェックリストでは、HSTS、CSP、X-Content-Type-Options、X-Frame-Options、Referrer-Policy、Permissions-Policy、Cache-Control、Set-Cookie の8つが、OK、要確認、未設定、不適切のどれかで出ます。

最後に、Server や X-Powered-By のような「実装の手がかり」があれば、別の枠で警告されます。入力欄は貼り替えるたびに再判定されます。

## 仕組み・計算式

貼った文字列を1行ずつ読み、最初の `:` より前を名前、後ろを値として取り出します。名前は大文字小文字を区別しません。HTTP/2 では小文字で届きますが、判定は同じです。

判定の基準は OWASP Secure Headers Project の推奨設定が下敷きです。HSTS は RFC 6797 のヘッダーで、`max-age` は秒単位です。ツールは86400で割って日数にし、15552000秒（180日）未満と、31536000秒（1年）未満を段階的に指摘します。CSP は W3C の Content Security Policy の仕様に沿って、`'unsafe-inline'`、`'unsafe-eval'`、ワイルドカード `*` といった弱い書き方を探すだけです。構文が正しいかどうかまでは見ていません。

X-Frame-Options は RFC 7034、Cookie の属性は RFC 6265 と、その改訂案（RFC 6265bis）の SameSite が根拠です。Cache-Control は RFC 9111 に書かれています。

## 計算例

出力はすべて、このツールの `script.js` を node で動かして確かめた値です。

**例1: 入力欄にある見本**

見本の10行（ステータス行を除くと9件）を判定すると、次の結果でした。

- HSTS: `max-age=15552000` は「約180日」で、要確認。1年未満で、`preload` が未指定です。
- CSP: 未設定。X-Content-Type-Options: `nosniff` で OK。
- Referrer-Policy: `no-referrer-when-downgrade` は旧ブラウザ既定値相当として、要確認。
- Cache-Control: `public, max-age=3600` は共有キャッシュにも残るため、要確認。
- Set-Cookie: `session_id` は「Secure属性なし、SameSite未指定」。
- 漏えい枠: `server`（nginx/1.18.0 (Ubuntu)）と `x-powered-by`（PHP/8.1.2）。

**例2: HSTS の境界値**

`max-age=15552000` は180日ちょうどなので、180日未満の指摘は出ません。1秒少ない `15551999` は、表示が同じ「約180日」でも「推奨の180日未満です」と出ました。`max-age=31536000; includeSubDomains; preload` は OK です。`max-age=31536000` だけでは `includeSubDomains` がないため、要確認でした。`max-age=300` は「約0日」と丸められます。

**例3: Cookie が複数あるとき**

`a=1; Secure; HttpOnly; SameSite=Lax` は妥当と判定されます。`b=2; SameSite=None` は、「Secure属性なし、HttpOnly属性なし、SameSite=NoneにはSecure属性が必須」と3つ出ました。2つ貼ると、Cookieごとに判定が並びます。

## よくある間違い

### 1. 全部 OK にしないと危ないと思う

ヘッダーの必要度はサイトで変わります。ログインのない静的サイトなら、`Set-Cookie` は出てきません。ここの判定は一般的な目安として使ってください。

### 2. `curl -I` の結果を、本番の動作そのものだと思う

`curl -I` は HEAD リクエストです。GET では付くヘッダーが、HEAD では付かない構成もあります。リダイレクト先まで見たいときは `-L` を付けます。ただ、複数の応答を貼ると同名のヘッダーが混ざるので、1つの応答ずつ貼るほうが読みやすいです。

### 3. 設定したつもりの値が、手前のプロキシで変わっている

アプリで消した `Server` が、前段のリバースプロキシで付け直されていることがあります。実際に外から見える値を確かめるのが、このツールの役目です。

### 4. HTTP のサイトに HSTS を付ける

HSTS は HTTPS の応答でだけ意味があります。RFC 6797 では、安全でない通信で受け取った場合、ブラウザは無視すると決めています。「未設定」が出たら、まず HTTPS で配信できているかを見てください。

## よくある質問

### Q. 「要確認」と「不適切」はどう違いますか？
A. 「要確認」は、推奨より弱いか、足りない部分があるという意味です。「不適切」は、`max-age=0` のように設定の意図が逆になっている値や、`max-age` の指定がない HSTS などを指します。

### Q. X-XSS-Protection は判定されますか？
A. 判定対象ではありません。一覧に出れば、意味の欄に「非推奨」と書かれます。XSS対策は CSP が中心です。

### Q. X-Frame-Options が未設定だと「要確認」になるのはなぜですか？
A. CSP の `frame-ancestors` でも同じ制限ができるからです。ただ、古いブラウザへの配慮として、併用が勧められています。

### Q. 値は外部に送られますか？
A. 送られません。貼ったヘッダーはブラウザの中で判定します。Cookie の値が含まれているなら、貼る前に消すか、他人に見せないようにしてください。
