この URL、どの location に落ちているのか。
`location /images/` を書いたのに、画像が別の設定で返ってくる。
正規表現は上から順なのか、長いほうが勝つのか。
このツールは、location の定義行とテストしたいパスを貼ると、各パスがどの location に決まるかを、理由付きの表で出します。

## 使い方

1. 設定ファイルから `location` の行だけを、1行に1つずつ貼ります。`location ~* \.(png|jpg)$ {` のように末尾の `{` が付いていても、無視されます。
2. 下の欄に、確かめたいリクエストパスを1行に1つ入れます。
3. 表に、各パスのマッチ先と判定理由が出ます。

行を足したり消したりすると、表はその場で変わります。

ここは見落としやすい点ですが、定義の並び順は結果に効きます。正規表現の location は、貼った順に調べられるためです。設定ファイルと同じ順で貼ってください。

## 仕組み・計算式

location の選び方は、nginx 公式ドキュメントの ngx_http_core_module（location ディレクティブ）に書かれています。ツールは、次の順で判定します。

- `=` 付きの完全一致が URI と一致したら、その場で決定します。
- modifier なし、または `^~` 付きの前方一致のうち、最も長く一致するものを1つ選びます。

ここで選んだものが `^~` 付きなら、正規表現は調べずに、そのまま決定します。付いていなければ、次に進みます。

- `^~` なしなら、`~`（大小文字を区別）と `~*`（区別しない）の正規表現を、設定ファイルの記述順に調べ、最初に一致したものを採用します。
- どの正規表現にも一致しなければ、先ほど選んだ最長の前方一致を使います。

前方一致の優劣は「長さ」で決まり、正規表現の優劣は「書いた順」で決まります。この2つのルールが違うことが、ほとんどの勘違いの元です。

正規表現の判定は、JavaScript の正規表現エンジンで行っています。nginx は PCRE を使うので、PCRE 固有の構文は同じ結果にならないことがあります。また、本物の nginx は、クエリ文字列を除いて正規化した URI に対して判定します。ツールは、貼ったパスをそのまま使います。

## 計算例

次の結果は、script.js と同じ判定を node で実行して確かめました。本物の nginx を動かして照合したものではありません。

**例1: 初期状態の定義（5行）とパス。** 定義は `= /favicon.ico`、`^~ /static/`、`~* \.(png|jpg|gif)$`、`~ \.php$`、`/` です。結果は次のとおりでした。

| パス | マッチ先 |
|---|---|
| /favicon.ico | `= /favicon.ico`（完全一致） |
| /static/images/logo.png | `^~ /static/` |
| /photo.png | 画像拡張子の `~*` |
| /index.php | `~ \.php$` |
| /about | `/`（最長の前方一致） |

`/static/images/logo.png` は、末尾が `.png` なのに、画像用の正規表現には行きません。`^~` が正規表現の検査を止めるためです。

**例2: 長い前方一致が、正規表現に負ける。** 定義を `/`、`/images/`、`~ \.php$`、`~* \.(jpg|png)$` にして、`/images/a.jpg` を入れると、`~* \.(jpg|png)$` になりました。`/images/` のほうが長い前方一致なのに、です。`/images/` だけを入れたときは、正規表現に一致しないので `/images/` が選ばれます。`/Z.JPG` も、`~*` が大小文字を区別しないので同じ正規表現に入りました。

**例3: 緩い正規表現を先に書く。** 定義を `~ ^/api/`、`~ ^/api/v2/`、`/api/` の順にして `/api/v2/users` を入れると、先に書いた `~ ^/api/` が採用されました。`^/api/v2/` のほうが具体的ですが、順番が後なので使われません。

**境界値: 末尾スラッシュの有無。** 定義が `/docs/` と `/doc` だけのとき、`/docs/` は `/docs/` に、`/docs` は `/doc` に決まります。1文字違いで、別の location に落ちました。

## よくある間違い

**正規表現は「より具体的」なほうが勝つと思う。** 勝つのは、書いた順で最初に一致したものです。例3のように、緩いものを上に書くと、下の具体的な行は一度も使われません。確かめるには、ツールで同じ順に貼って、パスを入れてみてください。

**前方一致も、書いた順で決まると思う。** 前方一致は逆で、一致した文字数が最も長いものが選ばれます。順番を入れ替えても結果は変わりません。「正規表現は順、前方一致は長さ」と分けて覚えると、混ざりにくいです。

**`^~` なしの長い前方一致で、正規表現を止められると思う。** 例2がその形です。静的ファイル用のディレクトリを守りたいなら、`^~` を付けます。意外だったのは、`^~` の有無だけで、同じパスの行き先が変わることでした。

もう1つ、`location /` を後ろに書けば優先度が下がる、という思い込みもあります。`/` は長さ1の前方一致なので、書く位置とは関係なく、ほかに一致がなければ使われるだけです。

## よくある質問

### Q. 同じ長さの前方一致が複数あるとどうなりますか？
A. 同じ長さで同じパスに一致する前方一致は、同じ文字列の location しかありません。本物の nginx は、同じ location の重複を設定の読み込みでエラーにします。ツールは、重複を貼ると先に書いたほうを表示しました。

### Q. `location /` は必須ですか？
A. 必須ではありません。ただ、どれにも一致しないリクエストの受け皿になるので、置いておくと、意図しない 404 を防ぎやすくなります。定義が `/docs/` だけで `/about` を入れると、「マッチする location なし」と出ます。

### Q. `@name` の名前付き location は判定できますか？
A. 判定できません。`@` で始まる行は、パスと一致する前方一致として扱われ、実際のリクエストには当たりません。名前付き location は、`error_page` や `try_files` から呼ぶ内部用のためです。

### Q. 正規表現が PCRE のものでも使えますか？
A. 文字クラス、量指定子、`$` でパス末尾を見る程度は、共通して使えます。先読みや名前付きグループなど、PCRE 固有の書き方は、結果が食い違うことがあります。
