障害調査で拾った、1700000000123 のような数字の列。
ログの時刻が全部エポック秒で、何時何分なのか読めない。
1行ずつ変換していたら日が暮れる。
このツールは、エポック秒・ミリ秒をまとめて貼ると JST・UTC・ISO 8601 に一括変換し、ログ全文からの数字の自動抽出と、日時からの逆変換、表計算用の TSV コピーまでできます。

## 使い方

1. 「エポック秒/ミリ秒 → 日時」の欄に、1行に1つずつ値を貼ります。全角数字でも半角に直して読み取ります。
2. ログをそのまま貼るときは「行中の10桁/13桁の数字を自動抽出する」にチェックを入れます。数字を含まない行は無視されます。
3. 表にはJST・UTC・ISO 8601が並びます。ISO 8601 の列だけ、セレクタで JST・UTC・ブラウザのタイムゾーンを選べます。

ここまでが「値 → 日時」です。続きは逆方向と、結果の持ち出し方です。

4. 「日時 → エポック秒」の欄には、`2026-09-10 21:00:00`、`2026-09-10T21:00:00`、`2026/09/10 21:00` のような形式を1行に1つ入れます。入力をどのタイムゾーンとして読むかは、下のセレクタで決めます。
5. それぞれの TSV 欄は「TSVをコピー」で丸ごとコピーでき、表計算ソフトにそのまま貼れます。

## 仕組み・計算式

UNIX時間（エポック秒）は、1970-01-01T00:00:00 UTC からの経過秒数です。POSIX（IEEE Std 1003.1）の「Seconds Since the Epoch」で定義されていて、うるう秒は数えません。1日はいつでも86,400秒として扱います。

このツールの単位判定は、桁数だけを見る独自の簡易ルールです。符号を除いた桁数が12桁以上ならミリ秒、11桁以下なら秒とみなします。現在時刻に近い値は、秒なら10桁、ミリ秒なら13桁になるので、ふつうのログならこれで足ります。

自動抽出モードの正規表現は「前後が数字ではない、ちょうど10桁、またはちょうど13桁の数字」です。14桁のIDの途中にある13桁は拾いません。

ISO 8601 の列は、`2023-11-15T07:13:20+09:00` のように時差つきで出します。この形式は ISO 8601 と、インターネット向けの日時書式を定めた RFC 3339 で説明されています。

日時から変換するときは、`Date.UTC` で UTC の時刻を求め、JST なら9時間を引きます。そのあと日付を計算し直して、入力と一致するか確かめます。2月30日のような日付は、丸めずに「存在しない日時です」というエラーにします。

## 計算例

数字は、このツールと同じロジックを node で動かして確かめました。

**例1: 秒とミリ秒の混在**

| 入力 | 判定 | JST | UTC |
|---|---|---|---|
| 1700000000 | 秒 | 2023-11-15 07:13:20 | 2023-11-14 22:13:20 |
| 1700000000123 | ミリ秒 | 2023-11-15 07:13:20 | 2023-11-14 22:13:20 |

同じ瞬間なのに、JST と UTC で日付が1日ずれます。9時間差の日付またぎは、何度見ても紛らわしいところです。

**例2: 初期表示の他の行**

- 1609459200 → JST で 2021-01-01 09:00:00
- 0 → JST で 1970-01-01 09:00:00
- -86400 → JST で 1969-12-31 09:00:00（UTC では 1969-12-31 00:00:00）

負の値は1970年より前の日時として読まれます。

**例3: 境界値（11桁と12桁）**

99999999999 は11桁なので秒として読まれ、JST では 5138-11-16 18:46:39 になります。999999999999 は12桁なのでミリ秒になり、2001-09-09 10:46:39 JST です。1桁違うだけで、3,000年以上ずれます。

**例4: 日時 → エポック秒（JST として解釈）**

- 2026-09-10 21:00:00 → 1789041600（ミリ秒は 1789041600000）
- 2026-01-01T00:00:00 → 1767193200
- 1970-01-01 09:00:00 → 0

2026-02-29 は、うるう年ではないので「存在しない日時です」になります。

## よくある間違い

**ミリ秒を秒として読んでしまう。** 13桁の値を秒として扱うと、年が数万年先になります。言語や基盤で単位が違うので、桁数を最初に見る癖をつけておくと安全です。ところで、変換結果の年がおかしいとき、まず何を疑いますか？ 桁数を数えるのが、いちばん早い確認です。

**JST と UTC の取り違え。** `2026-09-10 21:00:00` を JST ではなく UTC として入れると、結果は9時間ずれます。セレクタが「JST」のままか、必ず見てください。

**自動抽出で拾えない値。** 抽出の対象は10桁と13桁だけです。9桁の古い値や、14桁以上のマイクロ秒・ナノ秒は拾いません。一方、10桁の連番IDは時刻と区別がつかないので、拾ってしまいます。表の年月日が不自然な行は、元の行の意味を確認してください。

## よくある質問

### Q. 秒とミリ秒が混在していても大丈夫ですか？
A. 大丈夫です。行ごと（抽出モードでは数字ごと）に桁数を見て判定するので、混在したログでもそれぞれ正しく変換されます。

### Q. マイクロ秒やナノ秒は扱えますか？
A. 扱えません。JavaScript の日時がミリ秒精度までなので、対象は10桁前後の秒と13桁前後のミリ秒だけです。16桁の値を入れると、ミリ秒として読んだ遠い未来の日時が出てしまいます。

### Q. 「ブラウザのタイムゾーン」とは何ですか？
A. このページを開いている端末のタイムゾーンです。夏時間がある地域では、日付ごとにUTCとの差が変わりますが、ツールは日時ごとにその時点の差を使います。JST（UTC+9固定）の判定は、端末の設定に左右されません。

### Q. 2038年問題とは、このツールに関係しますか？
A. このツールは JavaScript の数値で計算するので、2038-01-19 03:14:07 UTC（エポック秒 2147483647）を過ぎても変換できます。2038年問題は、32ビット符号つき整数で秒を持つシステムの話です。
