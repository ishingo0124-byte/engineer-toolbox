`ECDHE-RSA-AES256-GCM-SHA384` と並んでいるけれど、どこまでが何の意味なのか。
サーバーの設定にある `DES-CBC3-SHA` は、消してよいスイートなのか。
IANA の名前と OpenSSL の名前を、いちいち表で引くのも面倒だ。
暗号スイート名を貼るだけで、鍵交換・認証・暗号・MAC に分け、前方秘匿性の有無と安全性の目安（推奨・許容・非推奨・危険）を表示します。

## 使い方

1. 暗号スイート名を1行に1つ、貼ります。`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` のような IANA 名、`ECDHE-RSA-AES128-GCM-SHA256` のような OpenSSL 名、TLS 1.3 の `TLS_AES_256_GCM_SHA384` に対応しています。
2. 各スイートが、鍵交換、認証、暗号（アルゴリズム・鍵長・モード）、MAC に分かれて出ます。前方秘匿性（PFS）の有無も、認証の行に付きます。
3. 判定は4段階です。理由は箇条書きで出ます。

入力欄の下に「N 件中 M 件を解析しました」と出るので、読み取れなかった行がすぐ分かります。

4. 下の折りたたみには、IANA 名と OpenSSL 名の対応表（53件）が入っています。

## 仕組み・計算式

TLS 1.2 のスイート名は `TLS_鍵交換_認証_WITH_暗号_MAC` の形で、RFC 5246 と、楕円曲線版の RFC 5289 に規定があります。このツールは対応表を引くだけでなく、名前の構造そのものを読んで分けます。そのため、表にないスイートも分解できます。TLS 1.3 は RFC 8446 の付録 B.4 で `TLS_暗号_ハッシュ` の形になりました。鍵交換は名前に含まれず、毎回使い捨ての鍵を使います。

OpenSSL 名は、IANA 名と1対1ではあっても規則的ではありません。`AES128-SHA` のように、鍵交換が省略されて静的RSAを意味したり、CBC の表記が消えたりします。`openssl ciphers` のマニュアル（ciphers(1)）を参照する必要があるのは、このためです。

判定の根拠は、RFC 7465（RC4 の使用禁止）、Sweet32（CVE-2016-2183、3DES と64bitブロック）、NULL・EXPORT・匿名鍵交換、MD5、前方秘匿性の欠如、CBC と SHA-1 の組み合わせです。これらを順に引き下げて、最終的な段階を決めています。簡易的な目安で、運用の可否を決める資料にはなりません。

## 計算例

出力はすべて、このツールの `script.js` を node で動かして確かめた値です。

**例1: 推奨になる構成**

`ECDHE-RSA-AES128-GCM-SHA256` は「推奨」です。別名は `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`、鍵交換は ECDHE、認証は RSA 証明書で前方秘匿性あり、暗号は AES 128bit の GCM（AEAD）でした。MAC の欄は SHA-256 ですが、これは MAC ではなく鍵導出に使うハッシュです。

**例2: 暗号は強くても、非推奨になる構成**

`TLS_RSA_WITH_AES_128_GCM_SHA256` は「非推奨」でした。AES-GCM でも、鍵交換が静的なRSAで前方秘匿性がないためです。長期の秘密鍵が後で漏れると、記録済みの通信が読めてしまいます。

**例3: 危険になる構成と、境界値**

`TLS_RSA_WITH_3DES_EDE_CBC_SHA` は「危険」で、別名は `DES-CBC3-SHA`、鍵長は実質112bitと出ました。`TLS_RSA_WITH_RC4_128_MD5` は、RC4 と MD5 の両方の理由が並びます。

境界の例も試しました。`TLS_ECDHE_ECDSA_WITH_AES_128_CCM_8` は、認証タグが8バイトと短いため「許容」止まりです。`ECDHE-RSA-AES256-SHA384` は、CBC モードなので「許容」でした。

## よくある間違い

### 1. `openssl ciphers -v` の出力を丸ごと貼る

行末に `TLSv1.2 Kx=ECDH Au=RSA` のような付加情報が続くと、全体が1つの名前として扱われます。`ECDHE-RSA-AES256-GCM-SHA384 TLSv1.2 Kx=ECDH Au=RSA` で試すと、判定は出ましたが、MAC の欄が「未知のMACトークン」になりました。別名も出ません。スイート名の列だけを抜き出してください。

### 2. 鍵長だけで安全性を比べる

同じ128bitの AES でも、GCM と CBC では事情が違います。GCM は暗号化と改ざん検知を一体で行いますが、CBC は別に MAC を組み合わせます。CBC のほうが一段下の評価になるのは、そのためです。

### 3. SHA-1 と SHA-256 の違いを、見落とす

`ECDHE-RSA-AES128-SHA` は「非推奨」ですが、末尾が違うだけの `ECDHE-RSA-AES128-SHA256` は「許容」でした。名前の最後の `SHA` は SHA-1 を指し、CBC と組み合わさると指摘の対象になります。`SHA256` や `SHA384` は別物です。一字違いで段階が変わるので、末尾までよく見てください。IANA 名でも OpenSSL 名でも、結果は同じでした。

### 4. 3DES を、鍵が長いから問題ないと思う

3DES は鍵が3本あるので長く見えますが、実質は112bitです。問題は鍵長より、64bitのブロックにあります。長時間続く通信で同じブロックが衝突するのが、Sweet32 の仕組みです。

## よくある質問

### Q. 「未認識」と出たのはなぜですか？
A. `TLS_` で始まらず、ハイフンも含まない名前は読めません。たとえば `AES128` だけの入力は未認識になりました。`TLS_FOO_WITH_AES_128_GCM_SHA256` のように、鍵交換の部分が未知の名前も同じです。

### Q. 「非推奨」が出たら、すぐ無効にすべきですか？
A. いえ、決める材料にとどめてください。古いクライアントとつなぐ必要があれば、残すことも現実にはあります。無効にする前に、実際の接続ログで使われているかを見るのが先です。

### Q. TLS 1.3 のスイートに鍵交換の情報がないのはなぜですか？
A. TLS 1.3 では、鍵交換の方式が拡張（key_share）で別に決まるからです。名前に含まれるのは、暗号とハッシュだけです。

### Q. 入力は小文字でも読めますか？
A. 読めます。`tls_ecdhe_rsa_with_aes_128_gcm_sha256` で試すと、「推奨」と別名つきで表示されました。
