tcp 3000 って、何のポートだったか。
ファイアウォールのログに、見覚えのない番号が並んでいる。
この番号は開けていいのか、それとも塞ぐべきなのか。
番号かサービス名を入れると、プロトコル（TCP/UDP）、用途、公開すると危ない理由までを、収録している約140件から引けます。

## 使い方

1. 検索欄に、番号（例: `443`）か、サービス名・用途の語句（例: `redis`、`リモートデスクトップ`）を入れます。全角の英数字は半角に直して検索されます。
2. 番号、サービス名、説明文、注意書き、プロトコルのどれかに部分一致した行が、カテゴリをまたいで残ります。一致のないカテゴリは、見出しの件数が「0/20」のように0になり、閉じたままです。
3. 一致のあるカテゴリは、自動で開きます。見出しをクリックすれば、手動でも開閉できます。
4. 各行には、番号、TCP/UDP、サービス名、用途が出ます。赤字の「注意」は、公開すると危ない理由や、置き換えを勧める理由です。

最初は何も入れずに、「Web・プロキシ」と「リモートアクセス」の2つが開いた状態から眺めるのがおすすめです。現場で触る頻度が高いのは、この2つだからです。

## 仕組み・計算式

掲載内容は、IANA（Internet Assigned Numbers Authority）の Service Name and Port Number Registry を主な典拠にしています。番号の範囲区分と登録の手続きは RFC 6335 に書かれています。

- 0〜1023: System Ports（Well-Known Ports）
- 1024〜49151: User Ports（Registered Ports）。MySQL（3306）や RDP（3389）はここです。
- 49152〜65535: Dynamic / Private Ports

区分は、ポートが「どう登録されるか」を示すもので、安全かどうかとは関係ありません。

もう一つ大事なのは、TCP のポート空間と UDP のポート空間は別物だということです（TCP は RFC 9293、UDP は RFC 768）。同じ「514」でも、TCP の514と UDP の514は別のサービスを指せます。

動的ポートは、クライアントが接続のたびに使う一時的な送信元です。RFC 6335 が示す範囲は49152〜65535ですが、多くの Linux は既定でそれより低い範囲（32768〜60999）を使います。Windows は49152〜65535です。サーバー側のログで1024以上の高い番号を見ても、通常は相手のクライアントの一時ポートです。

「業界慣行」の注記は、IANA に正式登録されていないが、現場で定着している番号につけています。8080、3000、5000、8000、2082〜2096（cPanel/WHM）、6667（IRC）などで、全部で20件です。

検索のロジックは単純です。入力文字列が、番号の文字列に含まれるか、サービス名・説明文・注意書き・プロトコルの文字列に含まれるか（大文字小文字は区別しません）を見ているだけです。

## 計算例

件数は、script.js のデータと検索の条件を node で実行して数えました。収録データを更新すると、件数は変わります。収録は138件で、画面の表示は「4 / 138 件が一致しました。」のようになります。

**例1: `443`**

4件が一致します。443/TCP の HTTPS、443/UDP の HTTP/3（QUIC）、6443/TCP の Kubernetes API サーバー、8443/TCP の HTTPS 代替です。443番が TCP と UDP の両方に出てくるのがポイントです。

**例2: `514`**

2件です。514/TCP は rsh（認証なしでリモートコマンドを実行する古いプロトコル）、514/UDP は Syslog です。どちらも「514」ですが、用途も危険度も別物でした。正直なところ、同じ番号でこれだけ危険度が違うのは意外でした。

**例3: `22`**

22/TCP の SSH と、2222/TCP の SSH 代替ポートの2件です。部分一致なので、「22」を含む番号が残ります。

**例4: 境界値と、ヒットしない例**

`1900` は2件です。1900/UDP の SSDP（UPnP）に加え、37/TCP/UDP の Time が出ます。Time の説明に「1900年からの経過秒数」とあるためで、番号は関係ありません。

`80` は7件です（80、8080、1080、8000、8009、8086、2380）。ほしいのは80だけでも、部分一致なので桁の一部が合う番号まで並びます。`xyz` は0件です。

## よくある間違い

### 1. 番号だけでサービスを決めつける

514番と513番は、TCP と UDP で別のサービスです。ファイアウォールのルールやログの調査で「514だから Syslog」と決めると、TCP の514（rsh）を見落とします。番号とプロトコルは、必ず組で確認してください。

### 2. 「開いている」と「そのサービスが動いている」を同一視する

8080 や 3000 のような慣行の番号は、設定ひとつで別のソフトウェアが使えます。逆に、SSH を2222で動かしている環境もあります。どのソフトウェアが待ち受けているかは、そのサーバーで確かめるしかありません。Linux なら `ss -tulpn`、Windows なら `netstat -ano` が出発点になります。

### 3. 1024以上のポートなら安全だと思う

範囲区分は登録の仕組みで、危険度ではありません。Redis（6379）、MongoDB（27017）、Elasticsearch（9200）、Docker Engine API（2375）は、全部1024より上です。認証なしでインターネットに公開された事例が多く、一覧にも注意書きをつけています。

### 4. 部分一致を完全一致だと思う

「80」で検索して7件出ても、バグではありません。番号がちょうど合うかは、行の先頭の太字の数字を見てください。

## よくある質問

### Q. 443番にUDPがあるのはなぜですか？
A. HTTP/3 が、TCP ではなく QUIC（UDP 上の転送方式）を使うためです。HTTP/3 は RFC 9114、QUIC は RFC 9000 に書かれています。ファイアウォールで443/TCP だけを許可していると、HTTP/3 は通らず、HTTP/2 などの TCP にフォールバックします。

### Q. 赤字の「注意」は、そのポートが危険という意味ですか？
A. 番号そのものが危険なのではなく、認証なしや平文のまま公開したときのリスクを書いています。VPN や内部ネットワークの中だけで使うなら、話は変わります。

### Q. 3000番や8080番は、必ずその用途ですか？
A. いいえ。どちらも開発者の慣習で、IANA の正式な割り当てではありません。実際に何が動いているかは、設定次第です。

### Q. Redis や MongoDB は、なぜよく話題になるのですか？
A. 既定では認証がなかったり、外部に公開しない前提だったりするのに、クラウドやコンテナの設定ミスで公開されてしまう例が多いからです。一覧の該当行に、注意書きを入れています。

### Q. 1024〜49151の番号は、自由に使っていいのですか？
A. 開発や検証で一時的に使うのは構いません。ただし他のソフトと衝突するので、共有するサービスで恒久的に使うなら、IANA の登録状況や社内の重複を確かめるのが無難です。
