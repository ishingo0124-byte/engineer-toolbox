ログに並ぶ「1700000000」、これはいつの話なのか。
10桁なのか13桁なのか、秒なのかミリ秒なのかが分からない。
手元の日時を、エポック秒に直したいだけなのに。
このツールは、エポック値から JST・UTC・ISO 8601 の日時を出し、逆に日時からエポック秒とミリ秒も出します。現在のエポック値は1秒ごとに更新されます。

## 使い方

1. ページを開くと、現在のエポック秒とミリ秒が出ます。横の「コピー」で、その瞬間の値を取れます。
2. 「エポック値」に数字を入れると、JST・UTC・ISO 8601 で日時が表示されます。単位は桁数から自動で判定します。
3. 判定がおかしいときは「単位の判定」で、秒かミリ秒かを自分で選びます。
4. 日時から変換したいときは、下の日時欄に入れます。入れた日時は JST として扱います。

ここまでが操作のすべてです。入力欄の数字は全角でも通ります。小数や数字以外の文字が混ざっていると、エラーの文が出ます。

## 仕組み・計算式

UNIX 時間は、1970-01-01T00:00:00 UTC を起点に、1日を86,400秒として数えた経過秒数です。POSIX（IEEE Std 1003.1）の「Seconds Since the Epoch」がこの定義にあたります。閏秒は数えません。

このツールの計算は、JavaScript の `Date` が土台です。ISO 8601 の文字列は `toISOString`（ECMA-262 で規定）で作っています。JST は UTC に9時間（日本標準時は UTC+9 固定）を足して出しています。

日時欄の入力は、閲覧しているブラウザのタイムゾーン設定を見ません。入れた値を、そのまま JST の壁時計の時刻として読みます。そのため、海外から開いても同じ結果になります。

単位の自動判定は、符号を除いた桁数が12桁以上ならミリ秒、11桁以下なら秒です。現在時刻の近くでは、秒が10桁、ミリ秒が13桁なので、この切り分けでほぼ足ります。

32bit 符号付き整数の範囲は、-2147483648〜2147483647 です。範囲を超えると、画面に注意書きが出ます。上限の 2147483647 は、2038-01-19 12:14:07 JST にあたります。

## 計算例

次の値は、script.js と同じ計算を node で実行して確かめました。

**例1: 1700000000（秒）。** 桁数は10桁で、秒と判定されました。JST は 2023-11-15 07:13:20、UTC は 2023-11-14T22:13:20.000Z です。日付が JST と UTC で1日ずれる時間帯なので、見比べると分かりやすいです。

**例2: 1700000000000（ミリ秒）。** 13桁なのでミリ秒と判定され、結果は例1と同じ時刻でした。同じ数字を「秒」として手動で指定すると、+055840-11-08T22:13:20.000Z という5万年台の日付になります。単位の選び間違いは、こういう形で表れます。

**例3: 2024-01-01 00:00:00（JST）。** 日時欄に入れると、エポック秒は 1,704,034,800、ミリ秒は 1,704,034,800,000 でした。結果は3桁区切りで出ます。UTC では 2023-12-31 15:00:00 にあたるので、UTC 基準の値と1日ずれて見えることがあります。

**境界値1: 2147483647 と 2147483648。** 2147483647 は 2038-01-19 12:14:07 JST で、注意書きは出ません。1増やして 2147483648 にすると 12:14:08 JST になり、32bit の範囲を超えたという注意書きが付きました。

**境界値2: 0 と -3600。** 0 は 1970-01-01 09:00:00 JST です。-3600 は 1970-01-01 08:00:00 JST で、UTC では 1969-12-31T23:00:00.000Z でした。

**境界値3: 12桁の数字。** 100000000000 は自動判定だとミリ秒になり、1973-03-03 18:46:40 JST です。秒として読みたければ、手動で指定します。その場合は 5138-11-16 18:46:40 JST でした。

## よくある間違い

**秒とミリ秒を取り違える。** JavaScript の `Date.now()` はミリ秒、多くの Unix 系の `date +%s` は秒を返します。13桁の値を秒の欄に入れた結果が、例2の5万年台の日付です。確かめるなら、桁数を数えてください。10桁なら秒、13桁ならミリ秒が典型です。

**UTC の時刻を、そのまま日本の時刻だと思う。** UTC と JST は9時間違います。ログの時刻が UTC のままなのに、日本の時刻だと思って障害の時間帯を探すと、半日ずれます。このツールは両方を並べて出すので、どちらの欄を読んでいるかを確認してください。

**閏秒があるのに、UNIX 時間は1日が常に86,400秒だと忘れる。** UNIX 時間は閏秒を数えません。TAI（国際原子時）と UTC の差は、2024年時点で37秒です。ミリ秒単位でログの前後関係を詰める場面では、同じ秒が2回現れる、または欠ける扱いになる実装もあります。

もう1つ、数字の世界の話をします。2038年問題です。古いシステムは、エポック秒を32bit 符号付き整数で持ちます。2038-01-19 12:14:07 JST を過ぎると、桁あふれが起きます。

正直なところ、意外だったのは「まだ先の話」では済まない点です。有効期限や返済日のように、将来の日付を持つデータは、2038年より先の日付を今のうちから扱います。32bit の項目に入れていれば、その時点で値があふれます。

## よくある質問

### Q. 桁数の自動判定は、どんなルールですか？
A. 符号を除いた桁数が12桁以上ならミリ秒、11桁以下なら秒です。100000000000（12桁）を入れて確かめると、ミリ秒と判定されました。古い日付の秒（9桁以下）や、遠い未来の秒は、取り違えやすいです。迷ったら手動で指定してください。

### Q. 負のエポック秒は、何を意味しますか？
A. 1970-01-01T00:00:00 UTC より前の日時です。-3600 を入れると、1969-12-31T23:00:00.000Z と出ました。負の値に対応していない実装もあるので、システム側の仕様は別に確認してください。

### Q. マイクロ秒やナノ秒の値は扱えますか？
A. 扱えません。JavaScript の `Date` がミリ秒までしか持てないためです。16桁前後のマイクロ秒は1000で、19桁前後のナノ秒は1,000,000で割ってミリ秒にしてから入れてください。

### Q. JST以外のタイムゾーンで、日時から変換できますか？
A. できません。日時欄は JST として読みます。別のタイムゾーンの時刻を変換するなら、UTC との差を自分で引いてから入れてください。
