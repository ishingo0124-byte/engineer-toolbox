長いURLを渡されて、どこまでがホストでどこからがパスなのか分からない。
クエリの `%E6%A4%9C...` が何の文字なのか読めない。
日本語ドメインを入れたら、何に化けるのかも見たい。
URLを貼るだけで、scheme・ホスト・ポート・パス・クエリ・フラグメントに分けて表示し、各要素を書き換えて組み立て直すこともできます。

## 使い方

1. 上の欄にURLを貼ります。入力と同時に、scheme・userinfo・host・port・origin・fragment が表に出ます。
2. パスは `/` ごとのセグメントで、クエリは `key=value` の1行ずつで、どちらもパーセントデコード後の値が並びます。同じキーが複数あっても、まとめずにそのまま複数行出ます。
3. ホストが日本語などの場合は、入力したままの表記と、ブラウザが実際に使う punycode（`xn--` で始まるASCII表記）を並べて出します。

ここまでが分解で、下の「組み立て」欄は別の道具です。

4. scheme、username、password、host、port、path、query、fragment を1欄ずつ入れると、ブラウザが正規化した1本のURLが出ます。上の入力欄とは連動しません。

なお、`example.com/path` のようにスキームを省いた入力は解析できません。`https://` から入れてください。

## 仕組み・計算式

URLの構造は RFC 3986 の `scheme://userinfo@host:port/path?query#fragment` が土台です。ただし、このツールの分解と組み立てはブラウザ標準の URL API で動いています。仕様でいうと WHATWG URL Standard です。実際にブラウザがリンクを解釈するときと同じ規則なので、手元で確かめた結果と食い違いにくくなっています。

日本語ドメインは、ホスト名を変換する IDNA の規則（UTS #46）で処理され、変換後は Punycode（RFC 3492）の `xn--` 形式になります。パーセントエンコードは、URLに置けないバイトを `%XX`（16進2桁）で書く仕組みで、日本語はUTF-8のバイト列に直してから並びます。

クエリの表は `URLSearchParams` を使っています。この読み方では `+` が空白になります。フォーム送信の形式（application/x-www-form-urlencoded）に合わせた規則です。一方、パスとフラグメントは `+` を空白にしません。同じ `+` でも、場所で意味が変わるわけです。

## 計算例

数字ではなく表示の例です。どれも、このツールと同じ `script.js` を node で動かして出た値です。

**例1: 全部入りのURL**

`https://user:pw@example.com:8443/p%20q/日本語?q=%E6%A4%9C%E7%B4%A2&a+b=c+d#frag%20x` を貼ると、次のようになりました。

- port は `8443（明示指定）`、origin は `https://example.com:8443`
- パスのセグメントは `p q` と `日本語`（`%20` が空白に戻る）
- クエリは `q` = `検索`、`a b` = `c d`（キーの `a+b` も値の `c+d` も `+` が空白）
- fragment は `frag x`（元は `#frag%20x`）

userinfo のパスワードは、画面では `**` と伏字になります。正直、ここで `+` が空白に化けるとは思っていませんでした。

**例2: 日本語ドメイン**

`https://例え.テスト/` を貼ると、host は `xn--r8jz45g.xn--zckzah` になり、Unicode表記の欄に `例え.テスト` が出ました。

**例3: 境界値（ポートと大文字）**

`https://example.com:443/` を貼ると、port は `443（https: の既定値。URL中には省略されています）` です。origin にも `:443` は付きません。`HTTP://EXAMPLE.com:80/a/../b/./c` なら、スキームとホストは小文字になり、セグメントは `b` と `c` だけが残りました。`..` と `.` は解決済みです。

組み立て欄に host=`example.com`、port=`443`、path=`/search`、query=`q=日本語&page=2` を入れた結果は、`https://example.com/search?q=%E6%97%A5%E6%9C%AC%E8%AA%9E&page=2` でした。

## よくある間違い

### 1. クエリの `+` を、そのまま `+` だと思う

検索キーワードが `a+b` のつもりで送ったのに、受け取った側で `a b` になる、という形で起きます。本物の `+` を送りたいときは `%2B` と書きます。表のデコード結果が空白になっていたら、これを疑ってください。

### 2. 既定ポートを書けば残ると思う

組み立て欄に port=`443` を入れても、`https` なら結果から消えます。バグではなく、正規化の仕様どおりです。逆に、`http` のURLに `:443` を入れると残ります。ポートが消えたと慌てる前に、scheme と見比べてみてください。

### 3. 不正な値が黙って捨てられる

組み立て欄の port に `99999` と入れても、エラーは出ません。結果は `https://example.com/` で、ポートだけが落ちていました。ポートの上限は65535です。出力を目で見ずに信じるのは、危ない場面です。

### 4. 日本語パスやクエリを、生のまま貼れば同じだと思う

画面上は日本語でも、サーバーに渡る形は `%E6...` の列です。ログやアクセス解析に出るのもこの形です。デコード前の値は、fragment なら「raw」の表示で見られます。

## よくある質問

### Q. userinfo のパスワードは外に送られますか？
A. 送られません。処理はすべてブラウザの中で動きます。画面には伏字で出ますが、「値」の欄では username と password を平文で出す作りです。画面共有の前には消しておくほうが安全です。

### Q. punycode から日本語に戻せますか？
A. このツールでは戻せません。Unicode表記の欄は、入力した文字列からホスト部分を抜き出して見せているだけで、逆変換はしていません。

### Q. 相対URLやスキームなしのURLは？
A. 解析できません。`https://` などから始まる絶対URLを入れてください。入れ直すと、すぐ結果が出ます。

### Q. 組み立て欄の結果が、上の分解結果と違うのはなぜですか？
A. 2つは独立しているからです。分解したURLを組み立て欄で試したいときは、各要素を手で写してください。
