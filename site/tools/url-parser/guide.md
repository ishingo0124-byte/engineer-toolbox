## 使い方

1. 上の欄にURLを貼り付けると、scheme・userinfo・host・port・origin・fragmentが即座に分解表示されます。
2. パスは`/`で区切られたセグメントごとに、クエリは`key=value`のペアごとに、それぞれパーセントデコード後の値で一覧表示されます（重複するキーはそのまま複数行表示）。
3. 日本語ドメインを含むURLでは、入力値のUnicode表記とブラウザが変換するpunycode（ASCII）表記を並べて表示します。
4. 下部の「組み立て」欄では各要素を個別に入力し、ブラウザのURL APIで正規化された1本のURLを組み立て直せます。上の解析欄とは独立して動作します。

## 仕組み・根拠

分解・組み立てのいずれも、ブラウザ標準のURL API（WHATWG URL Standard）をそのまま利用しています。RFC 3986が定義する`scheme://userinfo@host:port/path?query#fragment`の構造に基づき、URLオブジェクトの各プロパティ（protocol / username / password / hostname / port / pathname / search / hash）を読み書きして分解・再構築しており、パーセントエンコードや日本語ドメインのpunycode変換（IDNA、`xn--`から始まるASCII表記）はブラウザの実装に処理を委ねているため、実際のブラウザのURL解釈と一致します。

**現場の落とし穴**: ポート番号にスキームの既定値（httpsなら443）を明示指定しても、正規化時には自動的に省略されます。「組み立て」欄でport=443を入れても結果に現れないのは仕様どおりの挙動です。また、クエリ文字列の`+`は歴史的にスペース扱いされる場面がありますが、URL標準のパーセントデコードでは`+`はそのまま`+`として扱われる点に注意してください。

## よくある質問

### Q. スキームを省略したURL（例: example.com/path）は解析できますか？
A. できません。URL APIは絶対URLを前提としており、`https://`のようなスキームを含めて入力する必要があります。

### Q. userinfo（ユーザー名・パスワード）はそのまま表示されますか？
A. パスワードは画面上は伏字（`*`）で表示します。処理はブラウザ内で完結し、外部には送信されません。

### Q. punycodeを元のUnicode表記に戻せません。
A. 入力欄のホスト部分をそのまま抜き出して表示しているだけで、punycodeからUnicodeへの逆変換は行っていません。
