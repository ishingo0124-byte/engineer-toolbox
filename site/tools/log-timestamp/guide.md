サーバーAとBのログを並べたいのに、片方は「Sep 10 15:04:05」、片方は「2026-09-10T06:04:05Z」。
どちらが先に起きたのか、目で追っていると頭がこんがらがる。
しかも片方はUTC、片方はJSTかもしれない。
ログ行を貼ると日時の形式を自動で見分け、指定したタイムゾーンのISO 8601に統一して、複数ファイルなら時系列に並べ直します。

## 使い方

1. 上の欄に、形式が混ざったログ行をそのまま貼ります。1行ごとに判定するので、syslog、Apache/nginx のアクセスログ、ISO 8601、JSONログが同居していても構いません。
2. 「統一後のタイムゾーン」（JST、UTC、ブラウザの設定）を選びます。ここで選んだ値は、オフセットを持たない日時の解釈と、出力の表示の両方に使われます。
3. 「出力モード」を選びます。「行頭に付加」は各行の先頭に統一後の日時とタブを足します。「並べ替え」は元の行はそのままで、検出できた行だけを時系列に並べます。

ここまでが1ファイル分の使い方で、次からは複数ファイルを混ぜる場合です。

4. 下の「複数ファイルのマージ」に、ファイルA・B（・C）を貼ります。出力の行頭に [A]、[B]、[C] が付くので、どのファイルの行か分かります。
5. 日時のない行（スタックトレースなど）は、直前の日時つきの行の続きとして、一緒に動きます。

「検出: ◯行 / 未検出: ◯行」の表示も見てください。未検出が多いなら、対応外の形式です。

## 仕組み・計算式

行の中から日時を探す順番は決まっていて、先に見つかった形式が採用されます。

1. Apache/nginx の `[10/Sep/2026:15:04:12 +0900]` 形式
2. ISO 8601 / RFC 3339 に近い `2026-09-10T06:04:20Z` や `2026-09-10 15:04:05` 形式
3. 行頭の syslog 形式 `Sep 10 15:04:05`
4. JSON の `"timestamp"`・`"time"`・`"ts"`・`"@timestamp"` に入ったエポック秒（10桁）またはエポックミリ秒（13桁）、または行頭のエポック値

どの形式でも、最後は同じ計算になります。日時を「世界標準の絶対時刻（ミリ秒）」に直し、それを選んだタイムゾーンの表記に戻しているだけです。

```
絶対時刻 = 日時をUTCとして読んだ値 − オフセット
```

`+0900` なら9時間を引きます。オフセットがない日時には、選んだタイムゾーンのオフセットを当てます。

形式ごとの根拠は次のとおりです。

- syslog の `Mmm dd hh:mm:ss` は RFC 3164（BSD syslog プロトコル）の形式で、年もタイムゾーンも含みません。なので本ツールは年を「今年」、時刻を選んだタイムゾーンの壁時計時刻と仮定します。
- RFC 5424（新しい syslog プロトコル）は、年とタイムゾーンつきの RFC 3339 形式を使います。こちらは上の2番で拾えます。古い形式ほど情報が欠けています。
- Apache/nginx の `[dd/Mmm/yyyy:hh:mm:ss +hhmm]` は、Apache HTTP Server の mod_log_config で説明されている Common Log Format の `%t` です。オフセットつきなので、サーバーの設定に左右されません。
- エポック秒は、1970年1月1日 00:00:00 UTC からの経過秒です。

表示は秒までです。

## 計算例

数字は、script.js の検出・変換ロジックを node で実行して確かめました。syslog の「今年」は2026年として計算しています。ブラウザで開く時期によって、年は変わります。

**例1: 形式が違うのに同じ時刻の4行**（統一後 JST）

| 入力 | 統一後 |
|---|---|
| `Sep 10 15:04:05 myhost sshd[1234]: ...` | 2026-09-10T15:04:05+09:00 |
| `... [10/Sep/2026:15:04:12 +0900] "GET / ..."` | 2026-09-10T15:04:12+09:00 |
| `2026-09-10T06:04:20Z INFO starting up` | 2026-09-10T15:04:20+09:00 |
| `{"timestamp":"2026-09-10T15:04:25+09:00",...}` | 2026-09-10T15:04:25+09:00 |

3行目はUTCの06時ですが、JSTでは15時になります。9時間の差が目で追えない行でも、統一すれば並びがすぐ分かります。

**例2: 同じ syslog 行でタイムゾーンを変える**

Sep 10 15:04:05 は、JST を選ぶと 2026-09-10T15:04:05+09:00、UTC を選ぶと 2026-09-10T15:04:05+00:00 と表示されます。見た目は同じ15時ですが、指している瞬間は9時間違います。前者は UTC の06:04:05、後者は UTC の15:04:05 です。

同じ行でも、設定が違えば別の時刻になります。ログを出したサーバーが実際にどのタイムゾーンで動いていたかを、先に確かめてください。

**例3: 2ファイルのマージ**（初期表示の A、B）

A は 10:00:00、10:00:05（直後にスタックトレースの1行）、10:00:10。B は 10:00:02、10:00:07。結果は次の並びでした。

```
[A] Sep 10 10:00:00 web1 app: request start
[B] Sep 10 10:00:02 web2 app: request start
[A] Sep 10 10:00:05 web1 app: processing
[A]   at handler.process (app.js:42)
[B] Sep 10 10:00:07 web2 app: request done
[A] Sep 10 10:00:10 web1 app: request done
```


**例4: 境界値（年またぎ）**

`Dec 31 23:59:58` と `Jan  1 00:00:01` の2行を同じ年として並べ替えると、1月1日の行が先に来ます。実際は大みそかの行が3秒先ですが、年が入っていないので、このツールには判断できません。

## よくある間違い

### 1. syslogを「今年のログ」と思い込む

年がない形式なので、年末に出たログを年明けに処理すると、年が1年ずれます。上の例4がそれです。ログの更新日時や、ファイルを取得した日で年を確かめてください。年をまたぐログは、前半と後半に分けて貼ると安全です。

### 2. 行の途中の日時が優先されて、行頭が無視される

検出の順番は、Apache/nginx → ISO 8601 → syslog です。たとえば `Sep 10 15:04:05 host app: started at 2026-09-09T00:00:00Z` という行は、行頭の syslog ではなく、メッセージ中の ISO 8601 が採用され、2026-09-09T09:00:00+09:00 になりました。

正直なところ、これは意外でした。行頭の日時が勝つと思い込んでいたからです。「検出」の件数は合っているのに、並びがおかしいときは、これを疑ってください。

### 3. Apache のエラーログも同じ形式だと思う

アクセスログの `[10/Sep/2026:15:04:12 +0900]` は読めますが、エラーログの `[Wed Sep 10 15:04:05 2026]` は、node で確かめたところ未検出でした。別の書式なので、先に変換が必要です。

## よくある質問

### Q. エポック秒が桁の違う値のとき、どう判定されますか？
A. 10桁なら秒、13桁ならミリ秒として読みます。11桁や12桁は、どちらにも当てはまらず検出されませんでした。行頭の値は、後ろに単語境界が必要です。数字に別の文字がくっついていると、未検出になります。

### Q. 日時を検出できなかった行はどうなりますか？
A. 「行頭に付加」では行頭に「[検出できず]」が付きます。「並べ替え」では、末尾に注記つきで元の順序のまま並びます。マージでは、直前の行の続きになります。

### Q. 貼ったログはどこかに送られますか？
A. 送られません。ブラウザの中のJavaScriptだけで動いています。とはいえ、本番ログには個人情報やトークンが含まれることがあるので、貼る前にマスクしておくのが無難です。
